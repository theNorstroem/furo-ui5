# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this package is

`@furo/ui5` extends SAP's [`@ui5/webcomponents`](https://sap.github.io/ui5-webcomponents/) with a `bindData(fieldNode)` interface on top of `@furo/open-models`. Each Furo component subclasses the corresponding UI5 component and adds data-binding, FAT/meta/constraint handling, and value-state management — UI5 component APIs/events are inherited unchanged. The package ships JSX intrinsic types, a custom-elements manifest, and `web-types.json` for IDE completion against the wrapped components.

## Commands

- `npm start` — vite dev server (port 8080) + tsc watch. Loads `index.html` linking to `dev-playground/*.html` sandboxes. `/api/*` is proxied to `localhost:7070/api`.
- `npm test` / `npm run test:watch` / `npm run test:ui` — vitest **in a real Chromium browser** (`@vitest/browser` + Playwright). Specs are co-located: `src/elements/<name>/FuroUi5<Name>.spec.ts` (vite.config picks up `src/**/*.spec.ts`). Run a single file: `npx vitest run src/elements/text-input/FuroUi5TextInput.spec.ts`.
- `npm run lint` / `npm run lint:fix` — eslint with full type-checking (strict-type-checked + stylistic-type-checked + lit + lit-a11y + wc plugins).
- `npm run build` — full pipeline: `analyze` (public CEM) → `analyze:internal` → `analyze:deep` (writes/validates `web-types.json`) → `gen:intrinsic` (regenerates `src/JSX/*` from CEM) → `tsc` → `tsc-alias` (rewrites `@/*` imports **and** completes every relative specifier with `.js` / `/index.js` in the emitted `dist/` — see *ESM import specifiers* below) → `gen:exports`.
- `npm run gen:contracts` — regenerates `src/models/` from `.proto` files via `contracts/protoc-gen-open-models.sh` (requires `protoc` + the `open-models` plugin on PATH). The shell script reads from `contracts/proto` and `contracts/proto_dependencies` despite still naming `proto/` internally — run it from the repo root.
- `npm run storybook` — Storybook 10 on port 6006. Stories are co-located: `src/elements/<name>/FuroUi5<Name>.stories.ts`. Shared helpers/assets/MDX live in `src/stories-shared/`.
- `npm run audit:metadata` / `audit:metadata:strict` — check AI-retrieval metadata completeness across all tagged components (see *AI skills* below). `--json` for machine output; the `:strict` variant exits 1 on any gap or unknown category.
- `npm run skills:update` — regenerate the component reference docs consumed by the `furo-ui5-components` skill.

The husky `pre-commit` hook runs `npm run lint` and aborts if lint modifies files that weren't already staged — stage fixes before committing.

## Architecture

### Component shape (the pattern every web-component follows)
`src/elements/<name>/` contains:
- `FuroUi5<Name>.ts` — extends the UI5 element (e.g. `extends Input`), composes a small set of helper classes from `src/lib/open-models/`, exposes `bindData(fieldNode)` plus a `model` getter/setter, and re-emits UI5 events as needed.
- `index.ts` — re-exports the class (`export * from "./FuroUi5<Name>"`), calls `FuroUi5<Name>.define()`, and augments `HTMLElementTagNameMap`. This is the module consumers import, for registration *and* for the class/type — see *The per-component subpath is the public entry point* below.
- `FuroUi5<Name>.spec.ts` (optional) — vitest browser spec for the component.
- `FuroUi5<Name>.stories.ts` (optional) — Storybook story for the component.

The helper classes wire a component to `@furo/open-models`:
- `ModelReaderWriter` — dispatches by `fieldNode.__meta.typeName` to a typed reader/writer pair (see `StringReaderWriters`, `NumericReaderWriters`, `BoolReaderWriters`); add a new type binding here.
- `FatHandler<T>` — maps FAT `attributes` (e.g. `placeholder`, `maxlength`, `value-state`) onto component properties. Each component lists which FAT attributes it accepts in the constructor: `new FatHandler(this, ["placeholder", "maxlength"])`. Labels `hidden|readonly|disabled|required` are honored by default.
- `FieldNodeValueState` / `ReadonlyState` — synchronize UI5 value-state and readonly flags with the field node's state.

When adding a component, mirror an existing one (e.g. `src/elements/text-input/`) — including the `export * from "./FuroUi5<Name>"` line in its `index.ts`, which is what makes the class reachable — and register its `furo-ui5-*` tag in `src/Assets.ts`-adjacent registration if it must always be loaded. Adding it to `src/index.ts` is optional: the barrel is legacy surface and already covers only 93 of 131 elements, so prefer leaving new components to their subpath only.

### Generated code (do not hand-edit)
- `src/JSX/*` — regenerated by `npm run gen:intrinsic` from the CEM. Eslint ignores this directory; if a build complains here, re-run the generator. The generator copies the **literal text** of a component's `model` getter/setter type annotation into the generated file (resolving referenced type *names* to imports, e.g. `ARRAY`/`STRING`/`StringValue` → `@furo/open-models`, `FuroFatString`/`IFuroFatString` → `@/models`). Never alias that type with a local `type Foo = …` — `Foo` is emitted verbatim and breaks `tsc` (`TS2304: Cannot find name`); inline the full (union) type on `get model()` / `set model()` instead, as `FuroUi5MultiInput` / `FuroUi5MultiCombobox` do. Since vitest skips full typechecking, this only surfaces on `npm run build`.
- `src/models/*` — regenerated by `npm run gen:contracts` from `.proto`. Both eslint and `tsconfig` paths treat these as generated; the **barrel** is publicly exported as `@furo/ui5/models`, because names like `FuroFatString` / `IFuroFatString` / `NavigationNode` appear in the public signatures of component `model` accessors and consumers must be able to spell them. The per-file paths are deliberately **not** exported — do not add a `./models/*` wildcard: that would make ~200 modules of generated code, whose layout churns with the `.proto` files, part of the public API. Note `FuroFatString` is the `FieldNode` *class* while `IFuroFatString` is the plain-literal interface used by `initData` / `fromLiteral` / `toLiteral`; the two are not mutually assignable.
- `dist/`, `custom-elements.json`, `web-types.json` — produced by `npm run build`.

### Type renderers
`src/type-renderers/` ships one component per (context, type) pair — currently the full cross product of 4 contexts × 32 type slugs, 128 renderers. They are linted and typechecked like the rest of `src/`: there is no longer a `type-renderers-wip` exclusion in either `tsconfig.json` or `eslint.config.mjs`. They are **not** analyzed — both CEM configs exclude `./src/type-renderers/**/*.ts`, so no renderer appears in `custom-elements.json` (see *The per-component subpath is the public entry point* below).

The directory name *is* the tag name, and it follows a strict convention that `furo-ui5-typerenderer` depends on:

```
<context>-<type-slug>          e.g. display-google-protobuf-timestamp
```

- **context** — `display`, `cell`, `celledit`, `form`. Any other string works for renderers you supply yourself.
- **type-slug** — the field node's `__meta.typeName`, lowercased, with `.` and `_` replaced by `-`. Open-models primitives lose their `primitives.` prefix (`primitives.INT64` → `int64`), and `primitives.BOOLEAN` maps to `bool`.
- **repeated fields** append `-array` to the *item* type's slug (`display-string-array`); **map fields** append `-map` to the *value* type's slug (`display-string-map`). Neither exists yet — `furo-ui5-typerenderer` falls back to repeating the plain item/value renderer, so writing one is an optimization, not a requirement.

### furo-ui5-typerenderer
`src/elements/typerenderer/` resolves and instantiates the right renderer for any field node at runtime — it is what makes generic tables and generated forms possible. It is a normal `src/elements/` component (fully typechecked and linted, unlike the renderers themselves) and deliberately imports **no** renderer: consumers import the ones they need, and the element reports missing ones via a `renderer-missing` attribute/event after a 300 ms grace period.

Two things worth knowing when touching it, both of which come from `@furo/open-models` and are not obvious:
- `ARRAY.__meta.typeName` is the constant `"primitives.ARRAY<>"` and carries no item type. Resolve the item type from `atT(0)` or, for an empty array, the private `__getConstructor()` (same access as `FuroUi5SegmentedButton._detectModelItemType`).
- `MAP.__meta.typeName` is never assigned and stays `""`. Detect maps with `instanceof MAP` and take the value type from the parent's `FieldDescriptor.ValueConstructor` — its presence is also the only reliable descriptor-level way to tell a map field from a repeated one.

It renders into the **light DOM** with `display: contents` (a document-level adopted stylesheet, since light DOM has no `:host`), so the renderer participates in the surrounding layout and application CSS still reaches it.

### Path alias
`@/*` resolves to `src/*` (tsconfig + vite). After `tsc`, `tsc-alias` rewrites these to relative paths in `dist/`. Use `@/...` in source, never relative-up-out-of-src.

### The per-component subpath is the public entry point
Each element's `index.ts` does three things: it re-exports the class (`export * from "./FuroUi5<Name>"`), registers the tag, and augments `HTMLElementTagNameMap`. So `@furo/ui5/<component>` serves both roles and consumers never need the root barrel:

```ts
import "@furo/ui5/text-input";                                 // register the tag
import type { FuroUi5TextInput } from "@furo/ui5/text-input";  // erased — no module emitted
import { FuroUi5TextInput } from "@furo/ui5/text-input";       // class + registration
```

The `export *` line is **required** on every new element — without it the class is unreachable, which is how 38 elements ended up with no public type at all. It is deliberately placed in `index.ts` rather than exposed as a `./elements/<name>/<Class>` export: no new keys, and no filename frozen as public API (the same reasoning as the `./models`/`./types` wildcard note in `scripts/gen-exports.mjs`).

It is verified-inert for the build pipeline: the CEM analyzer emits `{kind:"js", name:"*"}` with **no** declaration, and all six downstream scripts gate on `declarations.length > 0`, so `web-types.json`, `src/JSX/**` and the generated skills docs are unchanged by it.

Note there is no way to get a class *without* side effects — every `FuroUi5*` extends a UI5 element whose dist module self-registers (`@ui5/webcomponents/dist/Input.js` ends in `Input.define()`; 126 UI5 modules do this, and none of the UI5 packages declare `sideEffects`). Scoping the cone to one element is the win; `import type` is the only truly free form.

The root barrel `src/index.ts` deliberately does **not** re-export the type renderers — the 30 `form-*` renderers each side-effect-import a registering element index, so re-exporting them made a single `import { FuroUi5Button } from "@furo/ui5"` define a dozen unrelated tags. Use `@furo/ui5/type-renderers/<slug>`.

**Type renderers follow the same subpath pattern**, and there is no renderer barrel. Each of the 128 `src/type-renderers/<slug>/index.ts` re-exports its class and registers its tag, so one specifier does both:

```ts
import "@furo/ui5/type-renderers/display-int32";                              // register
import type { DisplayInt32 } from "@furo/ui5/type-renderers/display-int32";   // name it
```

`./type-renderers` used to exist as a class barrel documented as "registers nothing". That was never achievable — the `form-*` renderers legitimately need `@/elements/form-row`, `@/elements/label` and an input element to render, so importing it reached 172 modules and defined 9 furo tags. It was removed; a per-renderer subpath reaches 5. Note `./type-renderers/*` did **not** cover the bare `./type-renderers` specifier (a subpath pattern needs the literal `./type-renderers/` prefix), which is why deleting the entry is what actually removes it.

The renderer keys are **enumerated, not a wildcard** — one `./type-renderers/<slug>` per directory, generated by `collectRendererEntries()` in `scripts/gen-exports.mjs` exactly like the 131 element keys. This is the one place the `./models` / `./types` "a wildcard would freeze every filename as public API" reasoning inverts: a renderer's directory name *is* its tag name, which `furo-ui5-typerenderer` resolves by convention, so it was already public. A subpath *pattern* does no existence check, so under `./type-renderers/*` every conceivable slug "resolved" — a typo failed at load with `ERR_MODULE_NOT_FOUND` instead of a clean `ERR_PACKAGE_PATH_NOT_EXPORTED`, and an unbuilt renderer could be advertised. `exports` is 273 keys as a result; adding a renderer directory is still zero config.

Renderers are **excluded from both CEM configs** (`scripts/deep-cem.config.mjs`, `scripts/internal-cem.config.mjs`), so `custom-elements.json` contains none of them and they have no generated reference docs, no `web-types.json` entries and no JSX intrinsics — all renderer docs are hand-written. They *are* linted and *are* in `tsconfig.json`, with no exclusions.

### Type-only imports are a bundle-size rule
`verbatimModuleSyntax` is on, so `import { type X } from "y"` keeps the statement and emits `import {} from "y"` — a side-effect import of the whole module. Only a top-level `import type` / `export type` is elided. Three ESLint rules enforce this (`consistent-type-imports` with `separate-type-imports`, `no-import-type-side-effects`, `consistent-type-exports`); keep them.

One gap to know: `consistent-type-exports` does **not** flag an export that already carries inline specifiers (`export { type X } from "y"`), so that form must be caught by review. `grep -rn 'import {} from\|export {} from' dist --include='*.js'` must print nothing — treat it as a post-build gate alongside the specifier check below.

⚠️ **`lint:fix` can silently delete a load-bearing side effect.** When the only use of an import is a type position, the autofix rewrites it to `import type` and the module stops being evaluated — along with any `customElements.define()` / `Registry.register()` it performed. This is usually right (that is the whole point), but it is wrong when the module was being imported *for* that side effect. `src/directives/nl2br.spec.ts` is the worked example: its helper defines `<nl2br-test-helper>`, so the type-only rewrite made the element never upgrade and `shadowRoot` come back null. The fix is an explicit bare import next to the type import, which also documents the dependency:

```ts
import "./nl2br-test-helper";                        // defines the element
import type { NL2BRHelper } from "./nl2br-test-helper";
```

After any bulk `lint:fix`, run the suite, and diff the module graph of a few `dist/**/index.js` entry points against the previous build if registrations are in play. Model-type registration specifically is *not* something an element should provide — see `src/stories-shared/ANY.mdx`, and `src/models/AnyRegistration.spec.ts` which pins the `@furo/ui5/models` barrel's registrations.

### ESM import specifiers in `dist/` (load-bearing config)
Source deliberately writes **extensionless** relative imports — `moduleResolution` is `Bundler`, so `tsc` accepts them and emits them verbatim. Node ESM and browsers loading modules natively both require full specifiers, so the emitted output is completed by the top-level `"tsc-alias"` block in `tsconfig.json`:

```jsonc
"tsc-alias": { "resolveFullPaths": true, "verbose": false }
```

`resolveFullPaths` appends `.js` to every relative specifier in `dist/**/*.{js,d.ts}` and turns directory imports into `/index.js`, verifying each against the emitted tree. **Do not remove it** — without it the package silently reverts to bundler-only and `import("./dist/index.js")` fails with `ERR_MODULE_NOT_FOUND` on the first internal hop. It also fixes the `allowArbitraryExtensions` CSS imports (`./table.css` → `./table.css.js`). This mirrors `tsconfig-ts-base.json` in the `eclipsefuro-web` monorepo, which the sibling Furo packages inherit.

Sanity check after touching the build: `grep -rhoE '"\.\.?/[^"]*"' dist --include='*.js' | grep -vE '\.(js|json)"$'` must print nothing.

⚠️ Run that gate against a **clean** `dist`. An incremental `npm run build` over an existing `dist` was observed once to leave `dist/JSX/index.js` with its 132 extensionless `import "./Avatar"` side-effect specifiers unrewritten, while every other file was completed correctly; `rm -rf dist && npm run build` produced a clean tree, and re-running `npx tsc-alias` on the stale tree also fixed it. Cause not pinned down — treat a gate failure confined to `dist/JSX/index.js` as a stale-tree artifact and re-verify from clean before chasing it.

### Keeping test artifacts out of the published package
`tsc` compiles specs, stories and test fixtures into `dist/` (they are needed there for nothing, but see the warning below for why they are still compiled). They are kept out of the **published tarball** by negation patterns in `package.json` `"files"`:

```jsonc
"files": ["./dist", "!dist/**/*.spec.*", "!dist/**/*.stories.*",
          "!dist/util/test-helpers/**", "!dist/stories-shared/**",
          "!dist/directives/nl2br-test-helper.*", ...]
```

This removes ~520 files (2705 → 2183, tarball 2.03 MB → 1.53 MB). Two gotchas:
- The negation patterns must **not** carry a `./` prefix. `"!./dist/**/*.spec.*"` is silently ignored by npm's packlist; `"!dist/**/*.spec.*"` works. Verify with `npm pack --dry-run --json --ignore-scripts` — the `--ignore-scripts` is required, because `npm pack` runs the `prepare` script and patch-package prints to stdout ahead of the JSON, which breaks any parse of the output (see *Patched dependencies* below).
- ⚠️ **Do not instead exclude these files from `tsconfig.json`.** It looks like the tidier fix (and the `eclipsefuro-web` base config does exclude `src/**/*.spec.ts`), but here it **breaks the test suite**: vite/esbuild applies the project's `compilerOptions` only to files the tsconfig actually matches, so an excluded spec is transpiled with default TS options instead of this project's `experimentalDecorators` / `useDefineForClassFields: false`. Empirically, excluding `src/**/*.spec.ts` makes `src/directives/nl2br.spec.ts` fail (`el.shadowRoot` is null — the element never upgrades). Keep specs inside `tsconfig.json`; that also keeps `npm run build` as their type gate, since vitest transpiles without typechecking.

### Testing
Tests run inside Chromium with `slowMo: 100` and devtools enabled. They use `@open-wc/testing-helpers` `fixture` + Lit `html`, vitest's `LocatorSelectors`, and `chai-a11y-axe` for a11y assertions (`await assert.isAccessible(el)`). Specs sit next to their component (`src/elements/<name>/FuroUi5<Name>.spec.ts`) and typically `import "@/Assets"` plus `import "./index"` to trigger registration, then `import { FuroUi5<Name> } from "./FuroUi5<Name>"` directly. Shared helpers live in `src/util/test-helpers/`. JUnit output lands in `test-results/junit.xml`; coverage is off by default (toggle in `vite.config.ts`).

The canonical reference spec is `src/elements/text-input/FuroUi5TextInput.spec.ts`. Its `describe` blocks tagged `[TEMPLATE]` (element identity & a11y, default model state, model → UI value sync, UI → model value sync, model-driven state, FAT attribute mapping, rebinding cleanliness, lifecycle) are designed to be copied into other element specs with only the tag name, model type(s), and FAT-attribute list changed. Blocks tagged `[element-specific]` cover element-only surface (custom events, methods like `clear()` / `closePopover()`). When writing tests for a new element, invoke the `test-element` skill (`.claude/skills/test-element/SKILL.md`) — it walks through the copy-and-adapt procedure and points at the reusable helpers (`createFatString`, `setInputValue`, `delay`).

### AI skills (`skills/`)
`skills/` holds agent skill packages. Only `skills/furo-ui5-components/references/` is machine-generated; everything else there is hand-written prose. SKILL.md front-matter is `name` + `description` only — **no `version` field**.

Claude Code only auto-discovers skills under `.claude/skills/`, so a package sitting in `skills/` is invisible to it — that is how a component's slots get invented rather than looked up. `.claude/skills/furo-ui5-components` is therefore a **symlink** to `../../skills/furo-ui5-components`; `skills/` stays the single source of truth (it is where `skills:update` writes) and git stores the symlink, so it survives a clone. Verified with `claude --debug -p …` on 2.1.220: the skill is listed, its body and `references/` load through the link, and no "unsafe or symlinked skill folder" warning appears. The other six packages are not linked yet — one `ln -s` each is all it takes.

The metadata pipeline is: **JSDoc tags on the element class → CEM analyzer plugin → `custom-elements.json` → generator → skill reference docs.**

Every element carries five AI-retrieval tags in its class JSDoc, alongside the existing `@tagname`/`@event`/`@slot` ones:

```ts
/**
 * @summary  Single-line text input field for user data entry.
 * @keywords input, text, field, form, textbox, entry, value
 * @category Form
 * @usecase  Use for single-line text entry like names, emails, or short values.
 * @related  furo-ui5-textarea, furo-ui5-multi-input, furo-ui5-combobox
 * @tagname  furo-ui5-text-input
 */
```

`@summary` is handled by the analyzer itself; the other four are hoisted onto the declaration by the `deep-cem` plugin in `scripts/deep-cem.config.mjs`. **Note the tag→field renaming**: `@usecase` → `useCase`, `@related` → `relatedComponents`. Adding a tag without also handling it there means it is silently dropped.

`@category` must be one of the values in `VALID_CATEGORIES` in `scripts/AuditComponentMetadata.js` (`Form`, `FormLayout`, `Button`, `Table`, `List`, `Navigation`, `Container`, `Layout`, `PageStructure`, `Display`, `Feedback`, `TypeRenderers`) — the audit fails on anything else.

When adding a component, add all five tags, then run `npm run analyze:deep && npm run audit:metadata` (coverage is currently 100% — keep it there) and `npm run skills:update`.

`skills/furo-ui5-components/references/components/*.md` and `components-index.md` are **generated — never hand-edit them**. `scripts/generate-webcomponents-skills-reference-docs.cjs` deletes every `.md` in that directory before writing. Per-component description overrides go in its `FALLBACK_DESCRIPTIONS` map. It reads the root `custom-elements.json` (the `analyze:deep` output, the only one with inherited UI5 members resolved), derives each `**Import:**` line from the `exports` map in `package.json` rather than the raw module path, and takes the class name from the module's own `src/` export — `declarations[0].name` reports the inherited UI5 base class, not the furo subclass.

### Peer dependencies & local linking
`@furo/layout` is pinned to a local `.tgz` path under `/Users/veith/Projects/theNorstroem/eclipsefuro-web/...` — `npm install` will fail on machines without that file. `npm run bootstrap` does `npm install && npm link && npm link @furo/ui5` for cross-package development against sibling Furo packages.

### Patched dependencies
`patches/` holds `patch-package` patches, applied by the `"prepare"` script on `npm install` / `npm ci`. Currently one: `@jackolope+lit-analyzer+3.2.1.patch`, which teaches the `no-missing-import` rule of the `@jackolope/ts-lit-plugin` language-service plugin to reverse-resolve a declaration through the owning package's `exports` map, so its suggested specifier is `@furo/layout/<subpath>` rather than the unresolvable on-disk `.../node_modules/@furo/layout/dist/...`. The same patch lives in the `Blueberry/web-starter` consumer app; keep the two in sync.

Three things to know before touching this:
- **The hook is `prepare`, not `postinstall`** (which is what the consumer app uses). npm runs a *dependency's* `postinstall` during a consumer's install, so `"postinstall": "patch-package"` would ship in the published `package.json` and make every `npm i @furo/ui5` fail on the missing `patch-package` binary. `prepare` runs locally and on `npm pack`/`publish`, but never for registry/tarball consumers.
- **`@jackolope/lit-analyzer` is pinned to exactly `3.2.1` via `overrides`.** It is a transitive dep (`ts-lit-plugin@3.1.6` declares `^3.2.1`), and patch-package matches on the version in the patch filename — without the pin, a 3.3.x release would silently stop the patch applying. If you intentionally bump it, re-cut the patch and rename the file. (`overrides` in a library's `package.json` is ignored by consumers, so this only affects local dev.)
- **`prepare` pollutes stdout on `npm pack`** — see the `--ignore-scripts` note under *Keeping test artifacts out of the published package*.

The plugin is IDE-only (no npm script invokes lit-analyzer's CLI), so a missing patch degrades quick-fix suggestions in WebStorm but never fails a build or CI. Restart the TS server after re-applying.

## Lint rules worth knowing

- `eslint-plugin-lit` is in `flat/all` mode (very strict), `eslint-plugin-wc` in `flat/best-practice`. `lit/quoted-expressions` requires `"always"`.
- `@typescript-eslint/no-explicit-any` is `error` — there is no escape hatch beyond `unknown` + narrowing.
- Lifecycle methods (`connectedCallback`, `firstUpdated`, `render`, `update`, `updated`, the `onPage*` route hooks, etc.) are whitelisted for `class-methods-use-this`.
- Imports use `import-x/order` with alphabetized groups and `newlines-between: always`.
- The actual `ignores` list is `**/*.js`, `**/*.html`, `**/*.d.ts`, `src/stories-shared/**`, `src/elements/**/*.stories.ts`, `.agents/**`, `dist/**`, `node_modules/**`, `src/x/models/**`. Note `src/type-renderers/**` and `src/models/**` are **not** ignored — they are linted and currently pass; `src/JSX/*` and `src/models/**` only carry rule *overrides*. Specs (`src/**/*.spec.ts`) are linted with a relaxed override (see `eslint.config.mjs`).
- `@typescript-eslint/consistent-type-imports` (`separate-type-imports`), `no-import-type-side-effects` and `consistent-type-exports` are bundle-size rules — see *Type-only imports are a bundle-size rule* above.
