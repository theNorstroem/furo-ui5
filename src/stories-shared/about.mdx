# フロー Furo UI5 components

The [SAP UI5 web components](https://ui5.github.io/webcomponents/) extended with data binding for Eclipse Furo open models (`@furo/open-models`).
The one thing every element here has in common is a `bindData(fieldNode)` interface that connects it to a field of your data model.

Most of them are the real UI5 element with exactly that added. A smaller set — `furo-ui5-tree-table`, `furo-ui5-money-input`, `furo-ui5-typerenderer` and the form layout elements among them — are Lit components written to cover ground the UI5 library does not, styled to match Fiori and bound the same way.

## What you get

- **The full UI5 component.** Where a UI5 counterpart exists, the Furo element subclasses it, so every property, slot, event, CSS part and theme works exactly as documented by SAP. Nothing is reimplemented and nothing is taken away.
- **Plus what UI5 does not ship.** Tables with a tree, a money input, generic type renderers and the form layout primitives are Lit components on our side. They are not UI5 elements, so their API is ours — but they carry the same `bindData()` interface and the same Fiori look.
- **Data binding on top.** Bind a field node and the element keeps itself and your model in sync, in both directions.
- **The enterprise standards come along.** Fiori design language, accessibility, i18n and theming are inherited from UI5.
- **IDE completion out of the box.** The package ships a custom-elements manifest, `web-types.json` and JSX intrinsic types, so your editor knows the tags, attributes and events. See [Using it with React](#using-it-with-react) for the typed `.tsx` story.

## Do you need this package?

The only thing `@furo/ui5` adds over stock UI5 is the `@furo/open-models` binding layer.

**If your project does not use `@furo/open-models`, use [`@ui5/webcomponents`](https://ui5.github.io/webcomponents/) directly.** Taking this package instead would mean an extra dependency and a second tag namespace in exchange for a feature you would never call.

That is not a one-way door. For every element that wraps a UI5 counterpart — the large majority — moving over later is a tag rename plus a `.model` binding, because the Furo element subclasses the UI5 one and every attribute, event handler and style you already wrote keeps working untouched. Only the Lit-based additions have an API of their own to learn.

## Install

```bash
npm i @furo/ui5
```

Import the elements you use — one subpath per element:

```js
import "@furo/ui5/text-input"; // register the element
import type { FuroUi5TextInput } from "@furo/ui5/text-input"; // its type, erased at compile time
import { FuroUi5TextInput } from "@furo/ui5/text-input"; // the class, and registers the element
```

Importing registers the custom element. There is nothing else to call.

Prefer the per-element subpath over the root `@furo/ui5` barrel. The barrel re-exports every
element, so pulling one name off it drags the whole set into your bundle; the subpath keeps
that scoped to the one element you asked for. Note that `import type` is erased entirely, so it
costs nothing and registers nothing — use it whenever you only need the type.

## Binding a model

`model` is a **property, not an attribute** — it carries a field node object, which cannot travel through an HTML attribute string. In lit that means the `.` prefix:

```js
import { html } from "lit";
import "@furo/ui5/text-input";

const entity = new CubeEntity();

html`<furo-ui5-text-input .model="${entity.description}"></furo-ui5-text-input>`;
```

Or imperatively, which is what the property setter does for you:

```js
const input = document.querySelector("furo-ui5-text-input");
input.bindData(entity.description);
```

Rebinding is safe: passing a different field node detaches the previous one and wires up the new one.

## What binding does for you

Once a field node is bound, the element takes care of the wiring you would otherwise write by hand:

- **Two-way value sync** — model changes update the UI, user input writes back to the model.
- **Value state** — validation state on the field node becomes the UI5 `value-state` and its message.
- **Readonly, disabled and required** — driven from the field node's state and meta.
- **Constraints** — field constraints are applied to the element, for example `max_length` becomes `maxlength`.
- **Accessibility defaults** — `placeholder` and `accessibleName` fall back to the field's meta if you did not set them yourself.

FAT types are supported as well. Each component declares which FAT attributes it honours; the component's own page lists them, together with the meta and constraints it reacts to.

## Using it with React

The package ships JSX intrinsic element declarations — one per component, generated from the custom-elements manifest — so the `furo-ui5-*` tags are fully typed in `.tsx`. Pull them in once, anywhere TypeScript sees them (your app entry or a `.d.ts`):

```ts
import "@furo/ui5/JSX";              // types every furo-ui5-* tag
import "@furo/ui5/JSX/TextInput";    // or just the one you need
```

These are type-only declarations — the emitted JavaScript is empty, so the import adds nothing to your bundle.

You then get completion and type-checking on every UI5 attribute, on the events, and on the `model` property, which is typed with the field types that component actually accepts:

```tsx
import "@furo/ui5/text-input";

export function DescriptionField({ entity }) {
  // model is typed as STRING | FuroFatString | StringValue
  return <furo-ui5-text-input model={entity.description} placeholder="Description" />;
}
```

**This requires React 19 or newer**, for two independent reasons:

- The declarations augment `declare module "react" { namespace JSX { interface IntrinsicElements … } }`. React 19 scoped the JSX namespace inside the `react` module; React 18 and earlier used a global `JSX` namespace, so the augmentation simply does not apply there.
- React 19 is the first version to pass non-primitive JSX props to custom elements as **DOM properties**. Earlier versions stringified them into attributes, which would turn a field node into `[object Object]`. `model={entity.description}` only works because of that change.

Attributes are written in camelCase (`accessibleName`, `showClearIcon`), and events as handler props (`onchange`, `onsearch-requested`), typed with their real UI5 detail types.

## Framework agnostic

Whatever an element is built on — a UI5 base class, Lit, or nothing at all — it is a regular web component.
They work anywhere you use HTML, with any framework or none at all.
As a result of following the best practices for building web components, our components are also [FBP](https://fbp.furo.pro/) friendly.

## Finding your way around

The sidebar groups the components by purpose: **input**, **display**, **form**, **layout**, **container**, **modal** and **navigation**.
Each component page opens with its import path, a link to the original SAP component and to the Fiori design guideline, followed by the bindable types it accepts and a live example.

If you want to render a field without picking a component yourself, start at **display/Typerenderer** — it resolves the right renderer for any field node at runtime.

If your API returns `google.protobuf.Any` fields, read **how to's/Unpacking google.protobuf.Any** — those resolve by type name at runtime, which is the one case where an import you might think is unnecessary actually is not.
